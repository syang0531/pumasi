# Pumasi 1.0.1

A patch release with fixes from the first user report on 1.0.0: GPU
drawing in Docker on Windows, and the Blender example.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows: `irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
Running agents pick it up with a cluster-wide upgrade
(`pumasi upgrade rollout`)
or a restart with the new binary. Agents and control planes of 1.0.0 and
1.0.1 work together; nothing in the protocol or the stored state changed.

## Fixes

- **GPU drawing in Docker on Windows.** Docker Desktop gives GPU
  containers `/dev/dxg` and CUDA but not `/usr/lib/wsl/lib`, the Windows
  driver's D3D12 libraries that Mesa draws with, so EEVEE, OpenGL and
  Vulkan fell back to the CPU (982 s instead of 20 s for the example's 24
  frames) and `pumasi gpu check --docker-run` reported no drawing. On
  Windows, NVIDIA tasks that ask for `capabilities = ["graphics"]` and the
  check now get Docker Desktop's `/usr/lib/wsl` read-only.
  `--docker-wsl-libs no` on the agent (and `--wsl-libs no` on the check)
  turns it off; `yes` turns it on elsewhere. Run
  `pumasi gpu check --docker-run --image IMAGE` again on Windows nodes so
  they get `gpu.graphics=true`.
- **OptiX on Windows** is reported as missing: it does not start in Docker
  Desktop containers, with or without that folder. Blender Cycles uses
  CUDA there.
- **Blender example** (`examples/blender-render`):
  - `render.sh` no longer forces Mesa's d3d12 driver when its library is
    missing (Blender crashed with exit code 139); it draws on the CPU and
    says so.
  - `scene.py` works with Blender 5.x (it failed on `HydraRenderEngine`).
  - A Python error in the scene script now fails the task instead of
    ending it as succeeded with no frames (`--python-exit-code 1`).
  - Rebuild the image to get these.
- **Windows checkouts**: a `.gitattributes` keeps shell scripts with LF
  line ends, so images built from a Windows clone start `render.sh`
  (it failed with `exec /opt/render.sh failed: No such file or directory`).
  The example's Dockerfile also strips CRs for existing clones.

## Changes that need attention

- This is the one exception to "Docker tasks get no host folders":
  read-only, a fixed path inside Docker Desktop's VM (not your Windows
  files), only graphics tasks on NVIDIA GPUs. See
  [docs/architecture.md](../architecture.md#gpu-drawing) and the
  [threat model](../threat-model.md).

# Pumasi 1.0.1 (한국어 요약)

1.0.0의 첫 사용자 리포트를 반영한 패치 릴리스입니다. Windows Docker의 GPU 그리기와 Blender 예제를 고쳤습니다. 1.0.0과 프로토콜·저장 형식이 같아 섞어 써도 됩니다.

- **Windows Docker GPU 그리기:** Docker Desktop은 GPU 컨테이너에 `/dev/dxg`와 CUDA만 넣고, Mesa가 그릴 때 쓰는 D3D12 라이브러리(`/usr/lib/wsl/lib`)는 넣지 않아 EEVEE·OpenGL·Vulkan이 CPU로 돌았습니다(예제 24장 982초, GPU는 20초). 이제 Windows에서는 `capabilities = ["graphics"]` NVIDIA 작업과 `gpu check --docker-run`이 Docker Desktop의 `/usr/lib/wsl`을 읽기 전용으로 받습니다. 에이전트의 `--docker-wsl-libs no`(확인은 `--wsl-libs no`)로 끕니다. Windows 노드에서 `pumasi gpu check --docker-run --image 이미지`를 다시 돌리면 `gpu.graphics=true`가 붙습니다.
- **Windows의 OptiX**는 Docker Desktop 컨테이너에서 시작하지 않아 '없음'으로 보고합니다. Cycles는 CUDA를 씁니다.
- **Blender 예제:** `render.sh`가 d3d12 라이브러리가 없을 때 d3d12를 강제하지 않고 CPU로 그립니다. `scene.py`가 Blender 5.x에서 동작합니다. 장면 스크립트의 파이썬 오류가 작업 실패로 기록됩니다. 이미지를 다시 빌드하세요.
- **Windows에서 받은 저장소:** `.gitattributes`로 셸 스크립트를 LF로 유지해 `render.sh`가 실행됩니다. 예제 Dockerfile도 CR을 지웁니다.
- 'Docker 작업에는 호스트 폴더를 넣지 않는다'는 원칙의 유일한 예외입니다. 읽기 전용, Docker Desktop VM 안의 고정 경로(Windows 파일이 아님), NVIDIA graphics 작업만 해당합니다.
