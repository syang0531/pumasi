# Pumasi 1.10.0

More of every GPU. A WebGPU task's timeout now stops a shader that never
ends; the cluster times untrusted WebGPU adapters with a GPU challenge,
so they are billed at their real speed; AMD and other GPUs without CUDA
are benchmarked; two jobs can share a GPU with `gpus = 0.5`; and NVIDIA
MIG slices are scheduled as GPUs of their own.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14, now minor 6) and the stored state's layout (7) are
unchanged; a 1.9 cluster upgrades with `pumasi upgrade latest` (or the
dashboard's Upgrade button). Upgrade the control plane first. WebGPU
challenges and jobs that need WebGPU features go only to 1.10 agents;
1.9 agents keep running everything else, half-GPU Docker tasks included.

## New

- **A WebGPU task's timeout stops its shaders.** A wasm task's GPU work
  runs in a separate process (`pumasi __webgpu-worker`, the same binary)
  that the agent ends at the task's timeout or when it is cancelled, so a
  shader that never ends no longer holds the GPU until the driver's
  watchdog resets it. The task ends as `timeout`, its stderr says the GPU
  work was stopped, and the GPU takes the next task. At most 16 dispatches
  wait on the GPU at a time. [`examples/webgpu/forever.toml`](../../examples/webgpu/forever.toml)
  shows it.
- **A GPU challenge over WebGPU.** The proof of work the cluster times
  providers' CUDA GPUs with now runs as a WGSL shader too (32-bit integer
  operations only, so every GPU computes the same hashes). Agents measure
  each adapter's hash rate, and the cluster times an untrusted node's
  adapters with it: a timed adapter is billed at what it measured (at most
  1.25 times what the cluster timed) instead of 1 TFLOPS at most, and a
  wrong answer is a strike and bills nothing. Answers are checked against
  the CPU on the agent before they are sent.
- **WebGPU features.** Devices are opened with `shader-f16` and subgroups
  where the adapter has them; `gpu = { features = ["shader-f16"] }` in a
  wasm job.toml sends the job only to adapters that have them. The
  adapter JSON a module reads lists the device's features and limits.
  `pumasi gpu webgpu` shows each adapter's features and hash rate.
- **AMD and other GPUs without CUDA are benchmarked.** An agent run with
  GPUs measures every GPU that the CUDA benchmark cannot (AMD, Intel,
  Apple, NVIDIA without CUDA) over WebGPU: FP32, memory bandwidth and the
  challenge's hash rate, instead of estimating them from the spec. The
  cluster times them with the challenge over WebGPU, so a provider's AMD
  GPU is billed at its real speed. Docker jobs on AMD GPUs get `/dev/kfd`
  and the GPU's render node with the groups that open them;
  [`examples/pytorch-cuda/job-rocm.toml`](../../examples/pytorch-cuda/job-rocm.toml)
  trains on one with PyTorch for ROCm.
- **Parts of a GPU.** `gpus = 0.5` (or `0.25`, any hundredth from 0.01 to
  0.99) gives a Docker task part of one GPU: tasks share the GPU, time
  sliced by the driver, as long as their parts add up to at most one, and
  each pays for its part of the GPU's FP32 rate and memory (the receipt
  says `RTX 3080 (0.5 GPU)`). The task's environment has
  `PUMASI_GPU_FRACTION`, plus `TF_FORCE_GPU_ALLOW_GROWTH` and
  `XLA_PYTHON_CLIENT_MEM_FRACTION` so TensorFlow and JAX do not take the
  whole memory (a job's own values win). Whole-GPU tasks wait for a GPU
  nobody shares. `pumasi label NODE gpu.share=off` keeps a node's GPUs
  whole. [`examples/pytorch-cuda/job-half.toml`](../../examples/pytorch-cuda/job-half.toml)
  runs two trainings on one GPU.
- **MIG slices.** An NVIDIA GPU in MIG mode is listed as its slices
  (`NVIDIA A100 MIG 1g.5gb`), each with its own memory, an FP32 estimate
  from its share of the GPU's SMs and its own UUID, and Docker jobs get a
  slice as a GPU of their own.
- **Who shares a GPU.** `pumasi node ID` and the dashboard note a shared
  GPU's runs and how much of it is in use.

## Notes

- Parts of GPUs are for Docker (and `executor = "image"`, which then
  runs on Docker) on GPUs Docker can use; a part is always of one GPU
  (`gpus = 1.5` is refused). WASM and microVM tasks take whole GPUs.
  Memory is shared on trust: the variables above ask frameworks to keep
  to their part, but nothing enforces it (MIG slices do enforce it).
  Schedules cannot ask for part of a GPU or WebGPU features yet. A part
  counts as one GPU against account quotas and `max_gpus_per_task`.
- A MIG slice is not benchmarked or challenged (its FP32 is estimated)
  and cannot be passed through to a microVM.
- Without a worker process (a library user's `Worker::Thread`), WebGPU
  work runs in the agent as before and a runaway shader is stopped by the
  driver's watchdog.
- Killing the worker ends the task at its timeout everywhere, but what the
  GPU does with the shader it was running is up to the driver: a software
  rasterizer stops with the process, while a virtual GPU (Apple's
  paravirtual device in macOS VMs, such as CI runners) can keep running it
  on the host until the host's watchdog, so the next GPU task there waits.
- The WebGPU challenge times the adapter, not a listed CUDA GPU: an
  adapter that is one of the node's listed GPUs is still checked as that
  GPU.
- Checked in CI: a never-ending shader stopped at its timeout (on
  lavapipe on Linux, and on Windows and macOS runners where they have an
  adapter), and a software rasterizer working right after; the WGSL challenge agreeing
  with the CPU; an adapter timed over WebGPU, billed in full after a right
  answer and at nothing after a wrong one; two half-GPU tasks sharing a
  GPU while a whole one waits, `gpu.share=off`, and billing by the part.
