# Pumasi 1.11.0

Windows machines nobody signs into now run Docker jobs, without Docker
Desktop: `pumasi docker setup` keeps Docker running in a small WSL distro
from boot. And Windows on Arm runs microVMs.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14, minor 6) and the stored state's layout (7) are
unchanged; a 1.10 cluster upgrades with `pumasi upgrade latest` (or the
dashboard's Upgrade button). Nothing changes on a machine until
`pumasi docker setup` runs there.

## New

- **Docker without Docker Desktop.** In an administrator terminal,
  `pumasi docker setup` installs Docker (Ubuntu's `docker.io`) in a WSL 2
  distro, `pumasi-docker`, made from Ubuntu Base 24.04, and registers a
  scheduled task that starts it at boot, before anyone signs in, and
  keeps `dockerd` running. A hidden local account, `pumasi-wsl`, owns the
  distro, because WSL does not run as the agent service's account; its
  random password is kept only by Task Scheduler. With an NVIDIA driver
  on Windows, the NVIDIA Container Toolkit goes in too, so GPU Docker jobs
  run there as they do with Docker Desktop. An agent with
  `--allow-docker` uses it as soon as it is set up, and starts the task
  again when Docker stops answering.
  - The daemon listens only on `127.0.0.1:2376` and only with mutual
    TLS: the client certificate is readable by SYSTEM and administrators,
    not by other local users. The distro sees no Windows drive and cannot
    start Windows programs. Everything lives in
    `C:\ProgramData\Pumasi\wsl-docker`.
  - `pumasi docker status` shows the task, whether Docker answers (and
    whether it has the NVIDIA runtime) and the end of its log; `pumasi
    docker remove` takes the distro, the task, the account and the files
    away.
  - Without WSL, setup installs it (`wsl --install --no-distribution`)
    and asks for a restart; the task then sets Docker up at boot by
    itself.
  - Docker Desktop stays supported: give the agent `--docker-bin` with
    Docker Desktop's CLI to keep using it on a machine with both.
- **MicroVMs on Windows on Arm.** `pumasi vm setup` installs QEMU 11.1's
  native Arm build. VMs use WHPX where Windows has the final Arm
  hypervisor API (Windows 11 24H2 and later) and software emulation
  before that; the agent boots one probe VM to tell, and no longer calls
  a VM accelerated when QEMU fell back to emulation.

## Changed

- Arm QEMU microVMs (Windows, and Linux hosts using QEMU) use a virtio
  console (`hvc0`); the pinned Arm kernels have no driver for the
  `virt` machine's serial port, so the guest console was silent there.

## Not adopted

- **An HCS backend.** A microVM backend on Hyper-V's compute service
  would need a second guest kernel with Hyper-V drivers and VHD disks.
  It is adopted only if it is clearly faster than QEMU with WHPX, which
  CI cannot measure (WHPX is nested on hosted runners).
  `scripts/windows/boot-times.ps1` times both on a real PC.
- **Signed Windows binaries** still wait for SignPath Foundation's
  approval ([signing.md](../signing.md)).

## Checked

- CI: `pumasi docker setup` on a hosted Windows runner (account, ACLs,
  pinned downloads, certificates, the task running as `pumasi-wsl`), and
  an agent's Docker jobs on the distro where the runner lets WSL 2 start
  one; `pumasi docker remove` after. A microVM on a Windows on Arm
  runner. Unit tests for the task definition, the setup script, the
  certificates (a mutual TLS handshake, refused without the client
  certificate) and the Arm QEMU command line.
- The distro's setup and start scripts in an Ubuntu Base chroot: Docker
  installed, `dockerd` answered the Docker CLI with the client
  certificate and refused it without one.
- By hand (QA): a fresh Windows PC without Docker Desktop runs Docker and
  GPU jobs after a reboot, before anyone signs in.
