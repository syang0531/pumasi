# Pumasi 1.13.0

Upgrades reach the control plane: `pumasi upgrade latest` (or the
dashboard's Upgrade button) now ends with every control plane replica and
every dashboard on the new version, without a terminal on their machines,
and a control plane whose new binary does not come back healthy puts the
old one back by itself. Also fixes for the three checks that failed now and
then in CI, each of which was a real bug.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The agent protocol (14, minor 6) and the stored state's layout (7) are
unchanged. A single 1.12 control plane upgrades itself to 1.13 with
`pumasi upgrade latest`, as it did since 1.3.1 (without the trial below,
which starts with 1.13). **With replicas, upgrade them to 1.13 by hand
this once** (followers one at a time, then the leader): a 1.12 replica
does not answer the new questions the 1.13 rollout asks. From 1.13 on they
upgrade themselves.

## New

- **The control plane upgrades itself.** After the agents' rollout has
  settled, a control plane installs the rollout's binary for its platform
  over its own (unless an agent on its machine shares the binary and does
  it) and restarts into it through its service manager.
  - **On trial, with a rollback.** Before restarting it keeps the running
    binary in `<cluster dir>/upgrade/previous`. The new binary counts its
    starts and commits once it has been healthy for 10 seconds (serving
    as the leader, or following a leader and caught up). A start that
    fails, a fourth start without a commit (a crash loop under the
    service manager) or no health within 5 minutes
    (`PUMASI_CP_TRIAL_SECS`) puts the previous binary back, restarts, and
    remembers the release so it is not installed again.
  - **Replicas one at a time.** Followers install the binary too. Each
    asks the leader for its turn; the leader lets one restart at a time,
    and only while the others answer, so a majority stays up. The leader
    goes last, once every other replica runs the new version: it steps
    down by restarting and the others elect a new leader in a couple of
    seconds. Running jobs carry on through it (CI checks that a job
    running across the leader's restart finishes and is paid once).
  - `pumasi upgrade status` (and `upgrade latest`, `upgrade rollout
    --wait`) lists each control plane: its role, platform, version, and
    whether it is current, waiting (and why), upgrading or rolled back.
    `upgrade latest` also fetches binaries for the replicas' platforms.
- **Dashboards follow.** A dashboard that shares its binary with the
  control plane restarts with it, and now also goes back down with it
  after a rollback. A dashboard alone on its machine (no control plane or
  agent there) installs the rollout's binary itself, checked against the
  cluster key in its admin ticket and the signed SHA-256, and restarts
  into it.

## Fixed

- **A restarted replica could not read its own log.** The purge point
  was written as an `Option` and read back as a plain log id, so after a
  log purge a replica that restarted asked for an entry at a nonsense
  index (31975955732986110) and would not start. Seen in CI as
  `three_replicas_survive_losing_the_leader` failing.
- **A failed control plane start kept its databases open**, so every
  retry in the same process failed with "Database already open".
- **The agent's cache could lose a download in progress.** The file
  store's garbage collection removed blobs that a running download had
  written but not yet tagged, and tasks failed with an I/O error (seen
  on macOS as `datasets_feed_sharded_jobs_and_outputs_come_back`). A
  download now holds a temporary tag on what it fetches.
- **A busy control plane took its own stall for silent nodes.** When the
  control plane's timer fell behind (a busy or slow machine), nodes that
  had sent heartbeats all along could be marked offline. Heartbeat
  deadlines now move by the time the control plane itself was stalled
  (seen on Windows as `selectors_drain_and_preemption`).

## Changed

- A control plane started from a terminal with no agent on its machine
  installs the rollout's binary over its own, as before, but now also on
  followers and with a trial. `--no-follow-binary` keeps it on its
  binary.
- The Long checks workflow soaks on Windows too, and runs each of the
  three once-flaky tests 50 times in a row on the runner it failed on.

## Known limits

- A binary with a newer agent protocol still needs the control plane
  upgraded first, by hand (the rollout refuses it without `--force`).
- When an agent on the control plane's machine installed the binary and
  the control plane then rolled back, the agent stays on the new binary
  (it is fine there); the control plane does not restart into that
  binary again.
- openraft 0.9 has no leadership transfer, so the leader steps down by
  restarting; a leader that comes back within the election timeout can
  win again (on the new version, so the upgrade is done either way).
- The Intel Mac runner's slow first answer after a control plane service
  restarts is not explained yet: the CI script now records what the
  client saw, the sockets and the processes when it happens.
