# Pumasi 1.14.0

For old Intel Macs, and microVM nodes in general: the second task of an
image starts in a booted guest that was waiting for it, microVM tasks can
checkpoint and resume elsewhere like Docker tasks, and Macs report their
CPU and GPU temperatures and GPU power, so the temperature alert works for
them. The Intel Mac build is now also built and tested on Apple Silicon
under Rosetta 2, ready for when GitHub retires its Intel runner.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The agent protocol is 14, minor 7 (1.13 was minor 6), and the stored
state's layout (7) is unchanged, so `pumasi upgrade latest` upgrades the
agents and then the control plane as in 1.13. MicroVM jobs that
checkpoint go only to 1.14 agents; until a node is upgraded it still takes
every other microVM job.

## New

- **Warm microVMs.** After a microVM task starts, the agent boots a spare
  guest of the same image and size in the background; the next such task
  takes it and skips the VM monitor's start, the kernel boot and the
  mounts (in CI under QEMU without KVM, about 260 ms instead of 1.8 s
  from start to exit; on an old Intel Mac most of a short task). A guest
  still runs one task and powers off, so nothing carries over between
  tasks.
  - At most one spare per image and size, two in all by default
    (`pumasi agent --warm-vms N`, `PUMASI_WARM_VMS`, `0` turns them off),
    within a quarter of the machine's memory, none on battery power, and
    each let go after 10 idle minutes.
  - On every backend: Firecracker, QEMU (also with WHPX on Windows) and
    Virtualization.framework. A guest that does not take its task within
    15 seconds is replaced by a normal boot, and the node stops keeping
    warm guests, with a warning in the agent's log.
  - Tasks with a network card or GPUs, and `pumasi vm run`, boot their own
    VM as before.
- **MicroVM checkpoints.** `checkpoint = true` now works for
  `executor = "microvm"` (and `"image"` on nodes without Docker). When the
  task has to move (preemption, `pumasi drain`, `--on-pause requeue`, a
  machine going to sleep), every process in the guest gets SIGTERM and the
  job's grace period, then SIGKILL. What it wrote to `/checkpoint` is
  stored like a Docker task's checkpoint, and the next run starts with it,
  on any node and any executor that checkpoints.
- **Mac sensors.** Intel Macs read the CPU die, integrated and discrete
  GPU temperatures and powers from the SMC; Apple Silicon Macs read GPU
  power from IOReport and CPU and GPU temperatures from the HID sensors.
  They show in `pumasi top`, the dashboard and `pumasi metrics`, and feed
  the temperature alert. `pumasi sensors` prints what this machine reads
  (`--raw` adds every key, in a format the tests can take as a fixture).

## Changed

- CI builds the `x86_64-apple-darwin` binary on Apple Silicon, checks its
  minimum macOS (10.15) and that it does not link Virtualization.framework,
  and runs it and the Intel test suites under Rosetta 2 (the `rosetta`
  job), next to the existing Intel runner jobs.
- A microVM's output disk has room for its checkpoint (up to the job's
  checkpoint limit), and an agent that starts again stops the warm guests
  a previous run left behind.

## Known limits

- Warm guests help only the second and later tasks of an image with the
  same CPUs and memory; the first task of an image, and tasks with a
  network or GPUs, boot cold.
- Warm guests under Virtualization.framework and WHPX, and the SMC and
  IOReport readings, are checked on real machines only: no CI runner can
  boot those guests or has those sensors. The parsing is tested against
  recorded output.
- A Mac's CPU package power is read (`pumasi sensors`) but not yet sent
  to the control plane.
- A microVM checkpoint is saved when the run moves, not periodically,
  like a Docker task's.
