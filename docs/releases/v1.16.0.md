# Pumasi 1.16.0

GPUs: a part of an NVIDIA GPU (`gpus = 0.5`) gets a memory limit from
NVIDIA's MPS server where the driver has one, MIG slices are benchmarked
and checked like whole GPUs, WebGPU tasks can draw (textures, samplers,
render passes, several bind groups) and use several GPUs at once, and
wasm jobs can be WASI preview 2 components.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The agent protocol is 14, minor 9 (1.15 was minor 8). The stored state
keeps its layout (7), so `pumasi upgrade latest` upgrades the agents and
then the control plane as in 1.15. Agents older than 1.16 keep working:
their parts of GPUs stay time-sliced, their MIG slices estimated, and wasm
jobs with `gpus = 2` or more are not sent to them.

## New

- **Memory limits for parts of NVIDIA GPUs.** On a Linux agent that runs
  as root and has Docker, the agent starts NVIDIA's MPS control daemon
  (`nvidia-cuda-mps-control -d`, from the driver packages) for its Volta
  or newer GPUs, or uses one that is already running. A part of such a
  GPU then runs as an MPS client: its container gets the daemon's pipe
  directory and `CUDA_MPS_PINNED_DEVICE_MEM_LIMIT` and
  `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` for its share, so an allocation
  past its part of the memory fails with an out-of-memory error while the
  other parts keep running. Where MPS cannot run (Windows and WSL have
  none, an agent as another user, an older GPU, no daemon binary, an
  image that runs as another user, `--no-gpu-mps`), parts are time-sliced
  and share memory on trust, as before. `pumasi node` and the dashboard
  say which: "memory limited by MPS" or "time-sliced, memory on trust",
  and an idle GPU with MPS says "parts get a memory limit (MPS)".
- **MIG slices benchmarked and checked.** CUDA shows a process one MIG
  slice, named in `CUDA_VISIBLE_DEVICES` before CUDA starts, so the agent
  measures each slice, and answers the GPU check for it, in a process of
  its own (`pumasi __cuda-slice`) running the whole-GPU kernels. Slices
  are billed from that measurement instead of a share of their GPU's
  figure.
- **Drawing over WebGPU.** Eight new `pumasi_webgpu` imports: `texture`
  and `sampler` (from WebGPU's descriptors as JSON), `render_shader` (a
  render pipeline from WGSL and a descriptor), `write_texture` and
  `read_texture`, `bind_group` (buffers, texture views and samplers for
  one `@group`), `dispatch_groups` (a compute dispatch with several bind
  groups) and `render` (one render pass: colour and depth attachments,
  bind groups, vertex and index buffers, viewport, scissor and draws).
  The JSON keeps WebGPU's names (`size`, `format`, `colorAttachments`,
  `loadOp`, `clearValue`, ...), so a descriptor written for the browser
  needs no changes. Textures count against the job's `memory_mb` like
  buffers. `examples/webgpu/render.toml` draws a sampled background and
  blended triangles and checks the picture against the CPU's.
- **Several GPUs per WebGPU task.** `gpus = 2` (up to 8) on a wasm job
  gives each task that many adapters of one node, fastest first, each
  billed. `adapters()` says how many the task has and `select(n)` which
  one new shaders, buffers and textures go to; objects stay on their
  adapter, and the adapter JSON says `index` and `count`. The job's
  `memory_mb` for GPU memory is split evenly between the adapters.
- **WASI preview 2 components.** A wasm job's module can be a component
  (`cargo build --target wasm32-wasip2`), run through Wasmtime's
  `wasi:cli/command` world with the same arguments, environment, files,
  limits and timeout as a core module. `examples/montecarlo` ships both.

## Changed

- The cluster sets `PUMASI_GPU_FRACTION` for a part of a GPU even when
  the job sets it, since the part (and now its memory limit) is the
  cluster's decision; the TensorFlow and JAX settings stay the job's.
- WebGPU buffers are also usable as vertex and index buffers.
- `pumasi agent` takes `--no-gpu-mps`, which leaves MPS off.

## Known limits

- MPS needs Linux, an agent running as root, Docker and a Volta or newer
  NVIDIA GPU, and serves only containers that run as root; Windows (the
  RTX 3080's PC) and WSL time-slice parts as before. MPS keeps tasks from
  taking each other's memory by accident; a hostile task could leave the
  limit, so MIG slices remain the hard boundary.
- The MPS limits are checked against a stand-in for the control daemon in
  CI, and on a real Linux GPU by hand.
- MIG slices are not passed through to microVMs; benchmarks of real
  slices are checked by hand (CI has no MIG GPUs).
- Components get no GPU: Wasmtime does not run `wasi:webgpu` yet, so
  WebGPU tasks stay core modules (`wasm32-wasip1`).
- A WebGPU task's several adapters come from one node; copies between
  them go through the module's memory.
