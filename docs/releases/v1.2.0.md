# Pumasi 1.2.0

The control plane and the dashboard as OS services, join tickets you can
list and revoke, microVMs that finish on macOS, and fixes from the first
day of real use of 1.1.0.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows: `irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
Running agents pick it up with `pumasi upgrade rollout` or a restart with
the new binary. The agent protocol and the stored state did not change,
so 1.2 agents and 1.0/1.1 control planes work together. Two admin calls
are new (`ListJoinTokens`, `RevokeJoinToken`): `pumasi token ls` needs a
1.2 control plane. The guest init changed (it powers off on macOS), so
the initrd hash changes: trust confidential-job launch measurements again
for 1.2 builds.

## New

- **`pumasi service install cluster` and `pumasi service install ui`.**
  The control plane and `pumasi ui` (with `-- --api-only` for the remote
  API) install as systemd units, launchd jobs or Windows services, like
  the agent, so a cluster comes back after its first machine reboots. A
  system service of these runs as the owner of its home, so the admin
  ticket stays the user's. `cluster` adds `--no-token`; `ui` listens on
  127.0.0.1:7400 by default, opens no browser and writes its sign-in link
  to `~/.pumasi/ui.url`. `pumasi service status` without a role shows
  every Pumasi service on the machine. The control plane, the dashboard
  and the agent stop cleanly on SIGTERM (`systemctl stop`, launchd).
- **Join tickets you can list and revoke.** `pumasi token ls` lists the
  join tickets and invites that can still be used, including the 24-hour
  one `pumasi cluster start` prints (now with its id), and `pumasi token
  revoke ID` (or the ticket itself) cancels one. The dashboard's Invites
  page has the same list with Revoke buttons.

## Fixes

- **macOS microVMs never finished.** The guest ended the VM with a
  reboot, which Virtualization.framework turns into a new boot: the guest
  started again, found its output disk already written, printed `no
  output disk` and rebooted again until the time limit. On the vz backend
  the guest now powers off. The guest also prints a last console line the
  host watches for, and the host reads all new console output, so a guest
  that reboots anyway is stopped and its result kept.
- **`sudo` installs on macOS made `~/.pumasi` root's.** macOS's sudo keeps
  `HOME`, so the agent's state went into the user's home owned by root,
  and `pumasi vm setup` then failed with `Permission denied`. Under sudo
  Pumasi now uses root's home (as Linux does), unless root already owns
  the user's `~/.pumasi` from an earlier install. The install script runs
  `pumasi vm setup` before installing the service when the options include
  `--allow-microvm`, and a permission error names the home and suggests
  sudo.
- **`ERROR relay_recv_channel closed`** after commands that worked: iroh
  logs it while an endpoint with a relay closes. It is no longer printed.
- **Logs redirected to a file** (`cluster start > cp.log 2>&1`) have no
  color escape codes; color is used only on a terminal, and `NO_COLOR`
  turns it off.
- **GPUs no job can use** say why: `pumasi node` and the dashboard's node
  page explain (Docker missing or unable to reach it, passthrough on Linux
  only, WebGPU for wasm jobs), and `pumasi status` points there.
  Integrated GPUs show `shared memory` instead of `0 MiB`.
- **`pumasi run` and `pumasi job`** show the last lines of a failed task's
  stderr, and list every task of jobs up to 100 tasks (was 20).
- **`pumasi top`** shows the hottest sensor, GPUs included, as the
  dashboard does (a Windows machine often reports only its GPU's).
- **Remote API job files:** one attached `.toml` under any name is the job
  file; with several, the error says to name it `job.toml`.
- **Dashboard:** the Cancel button goes away when a job ends without a
  reload; alert rules and the job example are in Korean on the Korean
  pages; chart axes show local time like the rest of the pages; the
  control plane's disk class reads "not given" instead of `unknown`.

# Pumasi 1.2.0 (한국어 요약)

컨트롤 플레인과 대시보드의 OS 서비스 설치, 목록·취소할 수 있는 참가 티켓, macOS microVM 수정, 1.1.0 실사용 첫날 보고 반영입니다. 에이전트 프로토콜과 저장 형식은 그대로라 1.0/1.1과 섞어 쓸 수 있습니다(`pumasi token ls`는 1.2 컨트롤 플레인이 필요). 게스트 init이 바뀌어 initrd 해시가 달라지므로, 기밀 작업의 부팅 측정값은 1.2 빌드 기준으로 다시 신뢰해야 합니다.

- **`pumasi service install cluster`, `pumasi service install ui`:** 컨트롤 플레인과 `pumasi ui`(원격 API는 `-- --api-only`)를 에이전트처럼 systemd·launchd·Windows 서비스로 설치합니다. 1번 기기를 재부팅해도 클러스터가 다시 뜹니다. 시스템 서비스는 홈 디렉터리 소유자 계정으로 돌아 관리자 티켓이 사용자 것으로 남습니다. `cluster`는 `--no-token`을 붙이고, `ui`는 기본 127.0.0.1:7400, 브라우저 안 열기, 로그인 링크를 `~/.pumasi/ui.url`에 씁니다. 역할 없이 `pumasi service status`는 이 기기의 서비스를 모두 보여 줍니다.
- **참가 티켓 목록·취소:** `pumasi token ls`가 아직 쓸 수 있는 참가 티켓과 초대(`cluster start`가 출력한 24시간 티켓 포함)를 보여 주고, `pumasi token revoke ID`(또는 티켓 자체)로 취소합니다. 대시보드 초대 화면에도 같은 표와 취소 버튼이 있습니다.
- **macOS microVM이 끝나지 않던 문제:** 게스트가 재부팅으로 VM을 끝내는데 Virtualization.framework는 VM을 다시 켜서, 게스트가 `no output disk`를 반복하다 시간 제한에 걸렸습니다. vz에서는 게스트가 전원을 끄고, 호스트도 새 콘솔 출력을 모두 읽어 재부팅 루프를 잡아냅니다.
- **macOS `sudo` 설치 시 root 소유 `~/.pumasi`:** sudo 아래에서는 root의 홈을 씁니다(이전 설치로 root 소유 `~/.pumasi`가 있으면 그대로). 설치 스크립트는 `--allow-microvm`이면 `pumasi vm setup`을 먼저 하고, 권한 오류에는 sudo 안내가 붙습니다.
- **기타:** 성공한 명령의 `ERROR relay_recv_channel closed` 제거, 파일로 받은 로그에 색 코드 없음, GPU를 못 쓰는 이유 안내(`pumasi node`, 대시보드), 통합 GPU는 `shared memory`, `pumasi run`/`job`에 실패한 태스크의 stderr 끝부분과 100개까지 태스크 줄, `pumasi top` 온도, 원격 API의 `.toml` 이름, 대시보드 취소 버튼·경보 규칙 번역·차트 현지 시각·디스크 표기.
