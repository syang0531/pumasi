# Pumasi 1.2.1

Windows fixes: say so when Smart App Control blocks a new binary, never
replace a working binary with a blocked one, and add the firewall rule for
direct connections that `pumasi service install` always failed to add.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
Nothing changed in the protocol or the stored state; 1.2.1 works with any
1.x control plane and agent.

## Fixes

- **Smart App Control.** Pumasi's Windows binaries are not code-signed
  yet, and Windows 11's Smart App Control blocks unsigned programs it does
  not know. An agent offered such a binary by `pumasi upgrade rollout`
  already kept its old one; `pumasi upgrade status` now says Windows
  blocked it, and why, instead of a bare OS error. The README's new
  "Windows Smart App Control" section says how to check and what to do.
- **`install.ps1` runs the download before it installs it**, so a binary
  Windows refuses to start (Smart App Control, an App Control or AppLocker
  policy) no longer replaces a working one. It also restarts the Pumasi
  services that are running, so they use the new binary.
- **Windows firewall rule.** `pumasi service install` on Windows gave
  netsh the binary's path in the `\\?\C:\...` form, which netsh refuses,
  so the rule that lets the agent and the control plane take direct UDP
  connections was never added and peers could fall back to the relay. The
  path is plain now, and CI checks the rule. Run `pumasi service install`
  again (as administrator) on Windows machines installed with 1.2.0 or
  earlier to add it.

## Code signing

Windows binaries carry version information now (product "Pumasi", in the
file's properties), and the release workflow can have them signed through
SignPath Foundation's free code signing for open source. That switches on
once the project is accepted and set up ([docs/signing.md](../signing.md));
until then releases stay unsigned.

## 한국어 요약

- 스마트 앱 컨트롤이 켜진 Windows에서 `upgrade rollout`으로 받은 새 바이너리가 막히면, `pumasi upgrade status`가 Windows가 막았다는 것과 그 이유를 알려 줍니다(이전 바이너리는 원래대로 계속 돎). README에 확인 방법과 대처를 적은 "Windows Smart App Control" 절을 추가했습니다.
- `install.ps1`은 받은 바이너리를 먼저 실행해 보고 설치하므로, 막힌 바이너리가 돌던 바이너리를 덮어쓰지 않습니다. 실행 중인 Pumasi 서비스도 새 바이너리로 재시작합니다.
- Windows에서 `pumasi service install`이 방화벽 규칙을 넣지 못하던 문제를 고쳤습니다(경로가 netsh가 거부하는 `\\?\` 형식이었음). 그래서 직접 연결 대신 릴레이로 붙을 수 있었습니다. 1.2.0 이하로 설치한 Windows 기기는 관리자 권한으로 `pumasi service install`을 한 번 더 실행하면 규칙이 들어갑니다.
- Windows 바이너리에 버전 정보(제품 이름 "Pumasi")가 들어가고, SignPath Foundation 무료 코드 서명이 승인·설정되면 릴리스 워크플로가 Windows 바이너리에 서명합니다([docs/signing.md](../signing.md)).
