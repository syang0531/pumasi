# Pumasi 1.20.0

Result checks. The control plane slips honeypot tasks with known answers
into providers' queues, so a provider that returns wrong results for
Docker, microVM or GPU work (which re-runs cannot check) is caught and
its account's earnings held; it times providers' disk and memory the way
it already timed their CPU, and every figure again each day; and each
node gets a score (uptime, checks and honeypots, finished runs) that
placement prefers and `pumasi node`, `pumasi score` and the dashboard
show.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The agent protocol stays 14 and goes to minor 11; the stored state keeps
its layout (7). `pumasi upgrade latest` upgrades the agents and then the
control plane as before. Agents older than 1.20 are not sent disk or
memory challenges (and providers among them have no `disk` label until
they are upgraded and timed); they still get honeypots, which are
ordinary tasks. The new commands need a 1.20 control plane.

## New

- **Honeypot tasks.** After a provider finishes a task, the control
  plane may send it a task whose answer it knows: 10% of the time for new
  providers (fewer than 10 passed checks and honeypots), 2% for others,
  25% after a strike, never on the owner's or trusted machines. Built-in
  honeypots are small seeded computations in the executor the provider
  just ran (a wasm module, or `sh` in an image for Docker and microVMs),
  named and sized like that task. Your own:

  ```sh
  pumasi honeypot add 7c1e04b2d9a8f310            # its succeeded tasks (16 at most)
  pumasi honeypot add 7c1e04b2d9a8f310 --task 3
  pumasi honeypot list
  ```

  An account honeypot is a copy of a finished task (not one that uses the
  file store); one of your own machines runs it again first, and only an
  answer that comes out the same is used, after that account's tasks. A
  wrong answer forfeits the run, strikes the node (so every result it
  returns is re-run, as after a failed check) and holds every earning of
  its account for a day (event `honeypot.failed`, alert `honeypot`);
  `pumasi honeypot release ACCOUNT` lets them go after their usual hold.
- **The policy:**

  ```sh
  pumasi honeypot set --new 100 --provider 20 --struck 250 --trusted 0   # per mille
  pumasi honeypot set --image python:3.12-slim   # image of built-in Docker/microVM honeypots
  pumasi honeypot set --hold 24h --retime 24h
  pumasi honeypot set --off
  ```

- **Disk and memory challenges.** Next to the CPU challenge, the control
  plane has a provider write seeded data with the page cache bypassed
  (256 MiB at most), read it back in an order it picks, follow a chain of
  dependent 4 KiB reads, and run the memory benchmark's kernel with a
  fresh seed, timing every step itself. A profile that claims over twice
  what it timed (twice in a row) or a wrong answer is a strike
  (`perf.inflated` event). On providers the automatic `disk` label is the
  class the cluster timed, never more than the profile says, so
  `disk=nvme` selectors can trust it.
- **Re-benchmarks.** The control plane times providers' CPU, disk and
  memory again every day (`--retime`, `0` for only when their benchmark
  changes); a timing below the last one by the benchmark-drop threshold
  raises the existing benchmark-drop alert.
- **A score per node,** 0 to 1000: (uptime over about a week + 2 x
  checks and honeypots + runs finished rather than lost) / 4; owner and
  trusted machines get full marks for checks, a suspended node 0.

  ```
  $ pumasi score
  NODE             LEVEL      SCORE  UPTIME  CHECKS    RUNS HONEYPOTS   LOST  DISK
  bob-pc           provider     925     98%     86%    100%       6/0      0  ssd (timed 512 MB/s, 96 us a read)
  carol-laptop     struck       525     71%     22%     95%       1/1      2  ssd (timed 420 MB/s, 110 us a read)
  ```

  Placement prefers the higher score among otherwise equal nodes.
  `pumasi node NODE` adds the score, honeypots and the cluster's disk and
  memory timings; the dashboard's node list has a Score column and each
  node page a Score section; Prometheus gets `pumasi_node_score`.

## Changed

- The agent's own memory and disk benchmarks use the challenge's code
  (benchmark version 2), so an honest machine measures what the cluster
  times. The first version 2 profile does not raise the benchmark-drop
  alert.
- A provider is not sent tasks while the cluster times its disk or
  memory (a second or two), as during the CPU challenge.

## Known limits

- Honeypots catch a provider that is often wrong, not one that cheats on
  a few tasks only, and they come right after a real task, which a
  provider watching for it could notice.
- Built-in honeypots use no GPU, and built-in Docker and microVM ones
  use one image (`busybox:1.36` unless set); GPU results are checked by
  account honeypots only. Account honeypots cannot use the file store,
  network allow lists, checkpoints or gangs, and are confirmed only while
  one of your machines is online.
- The disk challenge proves the work was done at that speed, not that the
  data was on the disk: an agent modified to keep it in memory passes.
  Disks that do not take direct I/O (tmpfs) are not challenged, and on
  macOS the page cache can serve the sequential read anyway, so there a
  disk is caught by its random-read latency (timed speeds stop at
  20,000 MB/s).
- The score's counters are written every 5 minutes; a failover can lose
  up to 5 minutes of them. Honeypots are managed in the CLI only.
- "An invited provider's score in the dashboard after a day of work" is
  checked by hand.

## 한국어 요약

- **함정 작업(honeypot).** 제공자가 태스크를 끝내면 컨트롤 플레인이 답을 아는 태스크를 보낼 수 있습니다. 새 제공자(검증·함정 통과 10번 미만) 10%, 그 밖의 제공자 2%, 스트라이크가 있으면 25%, 내 기기와 신뢰 기기는 0%. 기본 함정은 제공자가 방금 돌린 실행기로 도는 작은 시드 계산(wasm 모듈, Docker·microVM은 이미지 안의 `sh`)이고 그 태스크와 같은 이름·한도를 씁니다. `pumasi honeypot add <작업 ID> [--task N]`은 끝난 태스크를 복사해 계정 함정을 만듭니다(파일 저장소를 쓰지 않는 것만). 내 기기에서 한 번 더 돌려 답이 같을 때만, 그 계정의 태스크 뒤에 씁니다. 틀린 답이면 그 실행은 몰수, 스트라이크(이후 결과는 모두 재실행), 그 계정의 모든 수익을 하루 보류합니다(이벤트 `honeypot.failed`, 경보 `honeypot`). `pumasi honeypot release <계정>`으로 풉니다.
- **정책.** `pumasi honeypot set --new 100 --provider 20 --struck 250 --trusted 0`(천분율), `--image`(기본 Docker·microVM 함정의 이미지), `--hold 24h`, `--retime 24h`, `--off`.
- **디스크·메모리 챌린지.** CPU 챌린지 옆에서, 시드 데이터를 페이지 캐시를 우회해 쓰고(최대 256 MiB) 컨트롤 플레인이 고른 순서로 읽고 이어지는 4 KiB 읽기를 따라가게 하며, 메모리 커널을 새 시드로 돌리게 해 단계마다 직접 잽니다. 잰 값의 2배가 넘는 신고(두 번 연속)나 틀린 답은 스트라이크(이벤트 `perf.inflated`). 제공자의 자동 `disk` 라벨은 클러스터가 잰 종류를 따릅니다(신고보다 높지 않게).
- **재벤치마크.** 제공자의 CPU·디스크·메모리를 매일 다시 잽니다(`--retime`, `0`이면 벤치마크가 바뀔 때만). 지난번보다 벤치마크 하락 기준만큼 느려지면 기존 벤치마크 하락 경보가 울립니다.
- **노드 점수**(0~1000): (약 일주일 가동률 + 2 × 검증·함정 + 잃지 않고 끝낸 실행) / 4. 내 기기와 신뢰 기기는 검증 만점, 정지된 노드는 0. 배치는 다른 조건이 같으면 점수가 높은 노드를 고릅니다. `pumasi score`, `pumasi node <노드>`, 대시보드 노드 목록(점수 열)·노드 화면(점수 절), Prometheus `pumasi_node_score`.
- 에이전트 자체 메모리·디스크 벤치마크도 챌린지와 같은 코드를 씁니다(벤치마크 버전 2). 디스크·메모리를 재는 1~2초 동안은 태스크를 받지 않습니다.
- 에이전트 프로토콜 14(minor 11), 저장 레이아웃 7 그대로. 1.20 이전 에이전트는 디스크·메모리 챌린지를 받지 않고(그중 제공자는 업그레이드해 재기 전까지 `disk` 라벨 없음), 함정은 받습니다.
- 알려진 한계: 몇 개만 속이는 제공자는 못 잡음, 함정은 진짜 태스크 바로 뒤에 옴, 기본 함정은 GPU를 쓰지 않음, 디스크 챌린지는 데이터를 메모리에 두도록 고친 에이전트를 못 잡음, 장애 전환 때 점수 집계 최대 5분 손실, 함정 관리는 CLI만.
