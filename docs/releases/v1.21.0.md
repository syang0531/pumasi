# Pumasi 1.21.0

Cluster management. A task that exits non-zero, runs out of memory or
times out can be tried again (`retries`), on another node when there is
one; a job's failed tasks run again under the same id (`pumasi job
rerun`); a job can be held and let go (`pumasi job suspend|resume`);
Docker and WASM tasks can save a checkpoint on a period
(`checkpoint_every`), so a machine that dies without notice loses at
most that much; every run says what it really used (CPU time, peak
memory, disk and network), with a hint for tasks that asked for far
more; and schedules take network allow lists and caps.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The agent protocol stays 14 and goes to minor 12; the stored state keeps
its layout (7). `pumasi upgrade latest` upgrades the agents and then the
control plane as before. Agents older than 1.21 report no usage and are
not given runs with `checkpoint_every`. The new commands and job file
fields need a 1.21 control plane.

## New

- **Retries.** In job.toml:

  ```toml
  retries = 3                       # up to 100
  retry_on = ["exit:75", "oom"]     # default: exit, oom, timeout, error
  retry_delay = "30s"               # before the first retry (default 10s); doubles, up to 1h
  ```

  `exit` is any non-zero exit (and a WASM trap), `exit:N` one code,
  `oom` running out of memory, `timeout` the task's timeout and `error`
  a node that could not run it (an image that would not pull). The task
  sees `PUMASI_RETRY` (0, then 1, 2, ...). A retry goes to a node where
  the task has not just failed when one can take it. Retries do not count
  against `max_attempts` (which stays for lost nodes), each is billed as
  a run, and each raises a `task.retry` event.
- **Every attempt.** `pumasi job ID` and `pumasi describe job ID` list a
  task's attempts when it had several: the node, how it ended, the time,
  what it used and whether it was retried or rerun; the job's page in
  the dashboard has an "Attempts and usage" table.

  ```
  $ pumasi job 7c1e04b2d9a8f310
  ...
    runs: 3 retries on exit, oom, timeout, error (delay 10s, doubling)
    used: cpu 41.2s  memory 1.1 GiB  disk 12 MiB read 220 MiB written  net 4 KiB in 2 KiB out
    [3] attempts:
        attempt 1 node=desk exit 1 2100ms  cpu 1.9s  memory 310 MiB -> retried
        attempt 2 node=imac ok 2050ms  cpu 1.8s  memory 305 MiB
    hint [3]: asked for 4 GiB of memory and used at most 305 MiB
  ```

- **Reruns.** `pumasi job rerun JOB --failed` runs the failed and
  cancelled tasks again; `--task 3 --task 17` any finished ones. They
  keep the job's id and inputs and lose their last output and
  checkpoint; the other tasks keep their results.
- **Suspended jobs.** `pumasi job suspend JOB` holds a job: its queued
  tasks wait and its running ones go back to the queue (saving a
  checkpoint first where the job keeps them); `pumasi job resume JOB`
  lets it go on. A submitter can do both, and rerun, for its account's
  jobs. The dashboard has Suspend, Resume and "Rerun failed tasks"
  buttons.
- **Periodic checkpoints.** `checkpoint_every = "15m"` (10 s to 24 h,
  implies `checkpoint = true`): on that period the agent puts a file
  named `.pumasi-checkpoint` in the task's `/checkpoint`; the task saves
  its state there and deletes the file, and the agent stores the
  directory. The next run, after a move or after the node died, starts
  with the latest one. Docker and WASM tasks; a task that does not
  delete the file within its grace period is asked again next period.

  ```sh
  while work; do
    step
    if [ -f /checkpoint/.pumasi-checkpoint ]; then
      save_state > /checkpoint/state && rm /checkpoint/.pumasi-checkpoint
    fi
  done
  ```

- **What runs use.** Each run's CPU time, peak memory, disk bytes read
  and written and network bytes in and out, measured by its node: the
  container's cgroup (v2 or v1) for Docker on Linux, `docker stats`
  elsewhere, the VMM process and the network gateway for microVMs, the
  engine for WASM. `pumasi job`, `describe job`, the dashboard and the
  API show them per attempt and in total, and point out a task that used
  under a quarter of the memory or CPUs it asked for.
- **API:** `GET /api/v1/jobs/ID/runs` (attempts, usage, hints,
  suspension), `POST /api/v1/jobs/ID/rerun` with `{"failed": true}` or
  `{"tasks": [3, 17]}`, `POST /api/v1/jobs/ID/suspend` and `.../resume`.
- **Schedules with allow lists.** A schedule's job may have a microVM
  network allow list or cap (1.18), a part of a GPU, retries and
  `checkpoint_every`; `pumasi schedule add`, `cluster.toml` and the
  dashboard keep them.

## Fixed and changed

- A task that failed used to end its job's chance at once; with
  `retries` it does not. Without `retries` nothing changes.
- The placement order puts nodes a retry would rather avoid last, before
  every other preference.

## Known limits

- MicroVM jobs cannot have `checkpoint_every` yet (their checkpoint
  crosses the VM's disks only when the VM stops); an `executor =
  "image"` job with it runs as Docker.
- Gangs cannot have retries yet.
- Off Linux, Docker usage comes from `docker stats` every 2 seconds, so
  a short peak can be missed; a microVM's figures are its VMM process's,
  including the VMM's own memory. WASM CPU time is the thread's that ran
  it.
- A job long finished whose inputs the file store has collected cannot be
  rerun from them.
- "A long job on the home cluster survives pulling a PC's power plug" is
  checked by hand.

## 한국어 요약

- **재시도.** job.toml에 `retries = 3`(최대 100), `retry_on = ["exit:75", "oom"]`(기본: exit, oom, timeout, error), `retry_delay = "30s"`(첫 재시도 전, 기본 10초, 매번 두 배, 최대 1시간). `exit`는 0이 아닌 종료와 WASM 트랩, `exit:N`은 그 코드만, `oom`은 메모리 부족, `timeout`은 제한 시간 초과, `error`는 노드가 실행하지 못한 경우(이미지 받기 실패 등). 태스크는 `PUMASI_RETRY`(0, 1, 2...)로 몇 번째 재시도인지 압니다. 받을 수 있는 다른 노드가 있으면 방금 실패한 노드를 피합니다. 재시도는 `max_attempts`(노드 유실용)에 들어가지 않고, 실행마다 청구되며, `task.retry` 이벤트가 남습니다.
- **모든 시도.** `pumasi job ID`와 `pumasi describe job ID`가 시도가 여러 번인 태스크의 시도별 노드, 끝난 이유, 시간, 사용량, 재시도·재실행 여부를 보여 주고, 대시보드 작업 화면에 "시도와 사용량" 표가 생겼습니다.
- **재실행.** `pumasi job rerun JOB --failed`는 실패·취소된 태스크를, `--task N`(여러 번 가능)은 끝난 아무 태스크나 같은 작업 ID로 다시 돌립니다. 그 태스크의 이전 출력과 체크포인트는 지우고, 다른 태스크의 결과는 그대로입니다.
- **일시 정지.** `pumasi job suspend JOB`은 대기 중인 태스크를 붙잡고 실행 중인 태스크를 대기열로 돌려보냅니다(체크포인트를 쓰는 작업이면 먼저 저장). `pumasi job resume JOB`으로 이어 갑니다. 제출자 티켓도 자기 계정 작업에 쓸 수 있고, 대시보드에 일시 정지·재개·실패한 태스크 다시 실행 버튼이 있습니다.
- **주기적 체크포인트.** `checkpoint_every = "15m"`(10초~24시간, `checkpoint = true` 포함). 주기마다 에이전트가 태스크의 `/checkpoint`에 `.pumasi-checkpoint` 파일을 넣고, 태스크가 상태를 저장한 뒤 그 파일을 지우면 에이전트가 디렉터리를 저장소에 올립니다. 노드가 갑자기 죽어도 다음 실행은 마지막 체크포인트에서 시작합니다. Docker와 WASM만 지원하며, 유예 시간 안에 파일을 지우지 않으면 다음 주기에 다시 요청합니다.
- **실제 사용량.** 실행마다 CPU 시간, 최대 메모리, 디스크 읽기·쓰기, 네트워크 수신·송신을 노드가 잽니다(Linux Docker는 cgroup v2/v1, 그 밖은 `docker stats`, microVM은 VMM 프로세스와 게이트웨이, WASM은 엔진). `pumasi job`, `describe job`, 대시보드, API가 시도별·합계로 보여 주고, 요청한 메모리나 CPU의 4분의 1도 쓰지 않은 태스크를 짚어 줍니다.
- **API.** `GET /api/v1/jobs/ID/runs`, `POST /api/v1/jobs/ID/rerun`(`{"failed": true}` 또는 `{"tasks": [3, 17]}`), `POST .../suspend`, `POST .../resume`.
- **허용 목록이 있는 스케줄.** 스케줄 작업에 microVM 네트워크 허용 목록·대역폭 상한, GPU 일부, 재시도, `checkpoint_every`를 넣을 수 있습니다.
- 에이전트 프로토콜 14(minor 12), 저장 레이아웃 7 그대로. 1.21 이전 에이전트는 사용량을 보내지 않고 `checkpoint_every` 실행을 받지 않습니다.
- 알려진 한계: microVM은 `checkpoint_every` 미지원(image 작업은 Docker로 실행), 갱 작업은 재시도 미지원, Linux 밖 Docker 사용량은 2초 간격이라 짧은 최고치를 놓칠 수 있음, microVM 수치는 VMM 프로세스 기준, 저장소가 입력을 정리한 오래된 작업은 재실행 불가, 전원 플러그를 뽑는 시험은 수동.
