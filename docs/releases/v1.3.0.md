# Pumasi 1.3.0

Node names an admin chooses, and upgrading the whole cluster to the newest
release with one command or one button.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14) and the stored state's layout (7) are unchanged; the
admin calls below are new, so a 1.2 control plane does not know them.
**Upgrade the control plane's machine to 1.3.0 first** (the install script
restarts its services); from then on `pumasi upgrade latest` upgrades the
other nodes, including 1.2 agents.

## New

- **Rename nodes.** `pumasi node rename NODE NAME` (or the name field on
  the dashboard's node page, or `POST /api/v1/nodes/NODE/rename`) gives a
  node a display name. It shows in `pumasi status`, the dashboard, events
  and metrics, is the built-in `name` label, works wherever a command
  takes a node, and stays when the agent restarts with another `--name`.
  Names are unique; `--reset` goes back to the agent's name.
  `pumasi remove-node` now takes a name too.
- **Upgrade to the newest release.** `pumasi upgrade latest` (or the
  Upgrade panel on the dashboard's Nodes page, or `POST /api/v1/upgrade`)
  has the control plane download the newest GitHub release for every
  platform its nodes run, check each binary against the release's
  `SHA256SUMS`, its platform and its version, and roll it out the way
  `pumasi upgrade rollout` does (signed with the cluster key, idle nodes
  first, rollback on failure). `--check` shows the newest release and
  each node's version; `--version v1.3.0` picks a release.
- **The control plane and dashboard follow their binary.** When the agent
  on their machine installs a newer pumasi (or the install script does),
  `pumasi ui` restarts into it, and the control plane does once the
  rollout has settled. Browsers signed in to the dashboard sign in again.
  `--no-follow-binary` keeps the old behaviour.

## 한국어 요약

- **노드 이름 변경.** `pumasi node rename 노드 새이름`(대시보드 노드 화면의 이름 칸, `POST /api/v1/nodes/노드/rename`도 같음)으로 표시 이름을 바꿉니다. `pumasi status`, 대시보드, 이벤트, 지표, 기본 `name` 라벨, 노드를 받는 모든 명령에 적용되고, 에이전트가 다른 `--name`으로 다시 떠도 유지됩니다. 이름은 클러스터 안에서 겹칠 수 없고, `--reset`으로 에이전트 이름으로 돌아갑니다. `pumasi remove-node`도 이름을 받습니다.
- **최신 릴리스로 업그레이드.** `pumasi upgrade latest`(대시보드 노드 화면의 업그레이드 패널, `POST /api/v1/upgrade`도 같음)를 실행하면 컨트롤 플레인이 최신 GitHub 릴리스를 노드들의 플랫폼별로 받아 `SHA256SUMS`, 플랫폼, 버전을 확인한 뒤 `pumasi upgrade rollout`과 같은 방식으로 배포합니다(클러스터 키 서명, 한가한 노드부터, 실패 시 롤백). `--check`는 최신 릴리스와 노드별 버전만 보여 줍니다.
- **컨트롤 플레인과 대시보드의 자동 재시작.** 같은 PC의 에이전트(또는 설치 스크립트)가 새 버전을 설치하면 `pumasi ui`는 바로, 컨트롤 플레인은 롤아웃이 끝난 뒤 새 버전으로 재시작합니다. 대시보드에 로그인한 브라우저는 다시 로그인해야 합니다.
- **처음 한 번은 컨트롤 플레인 PC부터** 1.3.0으로 올려야 합니다(설치 스크립트가 서비스를 재시작). 그다음부터는 `pumasi upgrade latest` 하나로 나머지 노드(1.2 에이전트 포함)가 올라갑니다.
