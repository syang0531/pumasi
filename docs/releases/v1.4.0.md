# Pumasi 1.4.0

The five issues from the first weeks of real use: change what a service
runs with without reinstalling it, edit account policies from the
dashboard and the API, let a submitter see what it may submit and check a
job first, and show where each task's time went and which node ran it.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14) and the stored state's layout (7) are unchanged; a 1.3
cluster upgrades with `pumasi upgrade latest` (or the dashboard's Upgrade
button). Task times, node names and `?validate=1` need the control plane
on 1.4; the node's fetch, pull and upload times need the agent on 1.4.

## New

- **Service options without reinstalling** ([#42](https://github.com/syang0531/pumasi/issues/42)).
  `pumasi service status` prints the options each service runs with, and
  `pumasi service set` changes them and restarts the service:

  ```sh
  pumasi service set -- --allow-webgpu --no-allow-docker --slots 6
  pumasi service set ui -- --listen 127.0.0.1:7500
  ```

  It changes only what it names and keeps the rest: `--NAME [VALUE]` adds
  or replaces an option, `--no-NAME` removes it, `--dry-run` shows the
  result. The result is checked like the real command line before
  anything is written. No join ticket, no uninstall, and on Windows no
  reboot. The options now live in the service's home (`agent.toml`,
  `control-plane.toml`, `ui.toml`). A service installed by an older
  release keeps running as it is; `service status` says its options are
  still in the service definition, and its first `service set` moves
  them to the file.
- **Account quotas and job policies from the dashboard and the API**
  ([#43](https://github.com/syang0531/pumasi/issues/43)). The dashboard
  has an **Accounts** page: every account's quota, use and job policy,
  and a form where admins edit them. `GET` and `PATCH
  /api/v1/accounts/NAME/policy` are in `openapi.json` with a schema.
  PATCH changes only the fields it is given, and a list takes
  `{"add": [...], "remove": [...]}`:

  ```sh
  curl -X PATCH -H "Authorization: Bearer $PUMASI_ADMIN_TICKET" \
    -H 'Content-Type: application/json' \
    -d '{"images": {"add": ["node:22-slim"]}}' \
    "$PUMASI_URL/api/v1/accounts/lab/policy"
  ```

  The CLI has the same: `pumasi quota lab --add-images node:22-slim`,
  `--remove-images`, and `--add-`/`--remove-` for `executors` and
  `tolerations`. Removing the last entry of a list that means "any" when
  empty is refused.
- **Submitters can see their policy and check a job first**
  ([#38](https://github.com/syang0531/pumasi/issues/38)).
  `GET /api/v1/whoami` and `pumasi whoami` show a submitter ticket its
  account's job policy, quota and use. `POST /api/v1/jobs?validate=1`
  runs every check of a submission without creating the job: `200` with
  the nodes that would start it now (or why it would wait), or the same
  `403` or `400` and message a real submission gets. `capacity` in
  `/api/v1/status` counts only nodes the account's policy can use.
  `pumasi-remote check DIR` does the validation from the example client.
- **Where a task's time went** ([#40](https://github.com/syang0531/pumasi/issues/40)).
  Each task has `queued_ms`, `fetch_ms`, `pull_ms` (0 when the node
  already had the image), `run_ms` and `upload_ms`, in
  `GET /api/v1/jobs/ID`, `pumasi job ID` and the dashboard's job and task
  pages. `wall_ms` is `run_ms`, and it is what the receipt bills.
- **Node names in task views** ([#41](https://github.com/syang0531/pumasi/issues/41)).
  `node_name` next to `node` in the API, and `pumasi job ID` prints
  `node=NAME`.

## Changed

- **Docker tasks no longer pay for the image pull.** A Docker task's
  `wall_ms`, and so its receipt, used to start before `docker pull`; it
  now starts when the container is created, as microVM tasks already
  did. A task on a node with a cold image costs what it costs on a node
  with a warm one. The pull is reported on its own as `pull_ms`.
- The dashboard's job page shows "Queued" and "Run" columns in place of
  "Time".

## Notes

- A service installed or changed with 1.4 (`service install`, or the
  first `service set`) starts through `pumasi service run`, which older
  releases do not have on Linux and macOS. To take such a machine back
  to 1.3, reinstall its service with the 1.3 binary. Services that were
  installed before 1.4 and never changed with `service set` are not
  affected, and `pumasi upgrade` rollouts do not touch service
  definitions.
- Agents older than 1.4 report no `fetch_ms`, `pull_ms` or `upload_ms`
  (they read 0), and their Docker tasks still count the pull in
  `wall_ms`.
- By hand after upgrading: `pumasi service set -- --allow-webgpu` on
  each agent machine that should offer WebGPU, and add an image to an
  account from the dashboard's Accounts page.

## 한국어 요약

- **서비스를 다시 설치하지 않고 옵션 변경** (#42). `pumasi service status`가 각 서비스의 실행 옵션을 보여 주고, `pumasi service set -- --allow-webgpu --no-allow-docker`처럼 적어 준 옵션만 바꾼 뒤 서비스를 재시작합니다. `--이름 [값]`은 추가·변경, `--no-이름`은 삭제, `--dry-run`은 결과만 표시합니다. 참가 티켓도, 제거 후 재설치도, Windows 재부팅도 필요 없습니다. 옵션은 서비스 홈의 `agent.toml`(컨트롤 플레인은 `control-plane.toml`, 대시보드는 `ui.toml`)에 저장됩니다. 이전 릴리스로 설치한 서비스는 그대로 돌고, 처음 `service set`을 할 때 옵션이 파일로 옮겨집니다.
- **대시보드와 API에서 계정 쿼터·작업 정책 수정** (#43). 대시보드에 **계정** 페이지가 생겨 계정별 쿼터, 사용량, 작업 정책을 보고 관리자가 폼에서 고칩니다. `GET`, `PATCH /api/v1/accounts/이름/policy`가 스키마와 함께 `openapi.json`에 들어갔습니다. PATCH는 보낸 필드만 바꾸고, 목록은 `{"add": [...], "remove": [...]}`를 받습니다. CLI에도 `pumasi quota lab --add-images node:22-slim`, `--remove-images`(executors, tolerations도 같은 방식)가 생겼습니다.
- **제출자가 자기 정책을 보고 작업을 미리 검사** (#38). `GET /api/v1/whoami`와 `pumasi whoami`가 submitter 티켓에 계정의 작업 정책, 쿼터, 사용량을 보여 줍니다. `POST /api/v1/jobs?validate=1`은 작업을 만들지 않고 제출과 같은 검사를 해서, 통과하면 `200`과 지금 시작할 수 있는 노드(또는 기다리게 되는 이유)를, 아니면 실제 제출과 같은 `403`·`400`과 메시지를 돌려줍니다. `/api/v1/status`의 `capacity`는 계정 정책으로 쓸 수 있는 노드만 셉니다. 예제 클라이언트에는 `pumasi-remote check 폴더`가 생겼습니다.
- **태스크 시간 분리** (#40). 태스크마다 `queued_ms`(대기), `fetch_ms`(입력 가져오기), `pull_ms`(이미지 받기, 캐시에 있으면 0), `run_ms`(실행), `upload_ms`(출력 저장)를 API, `pumasi job ID`, 대시보드에서 보여 줍니다. `wall_ms`는 `run_ms`와 같고 영수증은 이 시간만 청구합니다.
- **태스크 표시에 노드 이름** (#41). API의 `node` 옆에 `node_name`이 있고 `pumasi job ID`는 `node=이름`을 출력합니다.
- **Docker 태스크는 이미지 받는 시간에 요금을 내지 않습니다.** 예전에는 Docker 태스크의 `wall_ms`(영수증)가 `docker pull` 전부터 시작했는데, 이제 microVM처럼 컨테이너를 만들 때부터 셉니다.
- **주의.** 1.4로 설치했거나 `service set`으로 바꾼 서비스는 `pumasi service run`으로 시작하므로, 그 기기를 1.3으로 되돌리려면 1.3 바이너리로 서비스를 다시 설치해야 합니다. 1.4 이전에 설치하고 `service set`을 하지 않은 서비스와 `pumasi upgrade` 배포는 영향이 없습니다. 1.4 미만 에이전트는 `fetch_ms`, `pull_ms`, `upload_ms`를 보고하지 않습니다(0으로 표시).
- **업그레이드.** 프로토콜(14)과 저장 형식(7)은 그대로입니다. 1.3 클러스터는 `pumasi upgrade latest`나 대시보드의 업그레이드 버튼으로 올라갑니다.
