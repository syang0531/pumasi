# Pumasi 1.4.1

A control plane that froze when a node could not start a task, and Windows
services that `Restart-Service` could not restart.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14) and the stored state's layout (7) are unchanged; a 1.3
or 1.4.0 cluster upgrades with `pumasi upgrade latest` (or the dashboard's
Upgrade button). The freeze is in the control plane: upgrading it is what
fixes it.

## Fixed

- **The control plane froze when a node could not start a task.** A node
  that cannot start a task (its input files did not arrive, the GPU the
  task was given is gone, the module does not load, preparing its mounts
  failed) reports that at once instead of a result. Taking that report,
  the control plane locked its state twice and waited for itself: from
  then on it scheduled nothing, answered no `pumasi` command, dashboard or
  API call, wrote no event, and did not stop when asked to. The log's last
  line was the job's `job submitted`. In every release since 1.0.0; found
  on a cluster where a GPU job sat for an hour after that line, until the
  control plane's process was ended by hand (the job then ran, on its
  second attempt). CI now refuses a lock taken in the operand of a `match`
  or `if let`, which is how the state was locked twice.
- **Windows: `Restart-Service` and `Stop-Service` failed on a Pumasi
  service that took more than 2 s to stop,** which a control plane with
  nodes or an agent with tasks does, and left it stopped: the service said
  "Running" until it had stopped, and PowerShell gives up on a service that
  does not say "StopPending". It says so now.
- **Windows: a service that did not stop stayed "Running" for ever,** since
  the Windows service manager, unlike systemd and launchd, never ends one.
  A Pumasi service that has not stopped 30 s after it was asked to now
  ends its process and reports itself stopped, so `Restart-Service` starts
  it again. The state on disk survives that like a power cut (it did before
  too).

## New

- **`pumasi service restart [agent|cluster|ui]`** stops a service and
  starts it again; without a role, every Pumasi service on the machine,
  the control plane first (`sudo` on Linux and macOS, an administrator
  PowerShell on Windows). Agents and the dashboard find a restarted
  control plane again by themselves, and it gives the tasks that were
  running to nodes again. Restarting an agent stops its tasks.

## 한국어 요약

- **노드가 태스크를 시작하지 못하면 컨트롤 플레인이 멈추던 문제**를 고쳤습니다. 노드는 태스크를 시작할 수 없을 때(입력 파일이 오지 않음, 배정된 GPU가 없음, 모듈을 읽지 못함, 마운트 준비 실패) 결과 대신 바로 실패를 보고합니다. 컨트롤 플레인이 그 보고를 받을 때 상태 잠금을 두 번 잡아 스스로를 기다렸고, 그 뒤로는 스케줄링, `pumasi` 명령, 대시보드, API, 이벤트 기록, 종료 요청이 모두 멈췄습니다. 로그의 마지막 줄은 그 작업의 `job submitted`입니다. 1.0.0부터 모든 릴리스에 있던 문제이고, GPU 작업 하나가 그 줄 뒤로 한 시간 동안 대기하다가 컨트롤 플레인 프로세스를 직접 끝낸 뒤에야(두 번째 시도로) 실행된 클러스터에서 찾았습니다. 이제 CI가 `match`나 `if let`의 조건에서 잠금을 잡는 코드를 거부합니다.
- **Windows에서 멈추는 데 2초 넘게 걸리는 Pumasi 서비스는 `Restart-Service`와 `Stop-Service`가 실패하고 서비스가 꺼진 채로 남던 문제**를 고쳤습니다(노드가 붙은 컨트롤 플레인, 태스크를 돌리는 에이전트). 서비스가 완전히 멈출 때까지 "Running"이라고 보고했기 때문이고, 이제 "StopPending"을 보고합니다.
- **Windows에서 멈추지 않는 서비스가 계속 "Running"으로 남던 문제**를 고쳤습니다. Windows 서비스 관리자는 systemd, launchd와 달리 서비스를 강제로 끝내지 않습니다. 이제 Pumasi 서비스는 중지 요청 뒤 30초 안에 멈추지 못하면 스스로 프로세스를 끝내고 중지됨으로 보고하므로 `Restart-Service`가 다시 시작합니다. 디스크의 상태는 정전 때처럼 안전합니다.
- **`pumasi service restart [agent|cluster|ui]`** 명령이 생겼습니다. 역할이 없으면 이 기기의 Pumasi 서비스를 컨트롤 플레인부터 모두 재시작합니다(Linux·macOS는 `sudo`, Windows는 관리자 PowerShell). 컨트롤 플레인을 재시작하면 에이전트와 대시보드가 스스로 다시 붙고 실행 중이던 태스크는 다시 배정됩니다. 에이전트를 재시작하면 그 노드의 태스크가 멈춥니다.
