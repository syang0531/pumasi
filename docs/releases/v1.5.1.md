# Pumasi 1.5.1

A dashboard or API behind a reverse proxy on another machine counted
every client as the proxy, so one client's wrong tickets blocked sign-in
for all of them. `--trusted-proxy` names the proxy.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14) and the stored state's layout (7) are unchanged; a 1.4
or 1.5.0 cluster upgrades with `pumasi upgrade latest` (or the
dashboard's Upgrade button). Only `pumasi ui` changed: upgrading the
machine that serves the dashboard or the API is enough.

## Fixed

- **Behind a reverse proxy on another machine, the failed sign-in limit
  applied to all clients together**
  ([#51](https://github.com/syang0531/pumasi/issues/51)).
  `--real-ip-header` is believed only on connections from the machine
  `pumasi ui` runs on, so with the TLS proxy on another host of the
  private network every client was counted under the proxy's address.
  Ten requests with a wrong ticket within a minute, from anyone who could
  reach the public name, then got everybody `429` on sign-in and on the
  API for 5 minutes, and could be repeated. Nodes, running jobs and
  browsers already signed in were not affected, and nothing was
  disclosed. Since `--real-ip-header` exists (1.0.0). Name the proxy with
  the new `--trusted-proxy` (below); nothing changes for a tunnel or
  proxy on the same machine.
- **A proxy that adds its own `X-Forwarded-For` line after the client's**
  (instead of appending to it) had the client's line read, so a client
  could pick the address it was counted under. The last line counts now,
  like the last address of a list.
- **An IPv4 client of a dual-stack listener** (`--listen [::]:7400`) was
  counted as `::ffff:a.b.c.d`, and one from this machine was not seen as
  local, so its `--real-ip-header` was ignored. Such addresses are read
  as IPv4.

## New

- **`pumasi ui --trusted-proxy ADDR[/PREFIX]`** (repeatable; an address
  or a network such as `192.168.1.0/24`): a reverse proxy on another
  machine whose `--real-ip-header` is believed, the same way it is for
  connections from this machine.

  ```bash
  pumasi ui --listen 0.0.0.0:7400 --no-open --login-only \
    --public-url https://pumasi.example.com \
    --real-ip-header X-Forwarded-For --trusted-proxy 192.168.1.20
  ```

  Give the address this machine sees the proxy connect from. In
  `X-Forwarded-For`, trusted proxies' addresses are skipped from the end,
  so a chain of them still yields the client. Whatever can connect from a
  trusted address picks the address it is counted under: let only the
  proxy reach the port, and have the proxy set the header itself (Caddy
  does by default; nginx: `proxy_set_header X-Forwarded-For
  $remote_addr;`). `0.0.0.0/0` is refused. For a service:
  `pumasi service install ui -- ... --trusted-proxy 192.168.1.20`.
- **`pumasi ui` warns at start** when it listens on another address than
  loopback with `--real-ip-header` and no `--trusted-proxy`, which is the
  setup above.
- **[docs/api.md](../api.md) says what counts towards the limit**: wrong,
  expired or revoked bearer tickets and failed sign-ins. A request
  without a ticket (a plain `401`, such as a scanner probing paths) does
  not count, and neither does a valid ticket without the role for a call
  (`403`).

## 한국어 요약

- **다른 기기의 리버스 프록시 뒤에서 로그인 실패 제한이 모든 클라이언트에 한꺼번에 걸리던 문제**를 고쳤습니다([#51](https://github.com/syang0531/pumasi/issues/51)). `--real-ip-header`는 `pumasi ui`가 도는 기기에서 온 연결에서만 믿기 때문에, TLS 프록시가 같은 사설망의 다른 호스트에 있으면 모든 클라이언트가 프록시 주소 하나로 집계됐습니다. 공개 주소에 닿을 수 있는 누구든 1분 안에 틀린 티켓으로 10번 요청하면 모든 사용자의 로그인과 API가 5분 동안 `429`가 됐고, 반복할 수 있었습니다. 노드, 실행 중인 작업, 이미 로그인한 브라우저는 영향이 없었고 노출된 정보도 없습니다. 새 옵션 `--trusted-proxy`로 프록시를 지정하세요. 같은 기기의 터널이나 프록시는 달라지는 것이 없습니다.
- **`pumasi ui --trusted-proxy 주소[/프리픽스]`**(여러 번 가능, `192.168.1.0/24` 같은 네트워크도 가능)가 생겼습니다. 그 주소에서 온 연결의 `--real-ip-header`를 이 기기에서 온 연결과 똑같이 믿습니다. 이 기기에서 보이는 프록시의 주소를 주세요. `X-Forwarded-For`에서는 신뢰하는 프록시의 주소를 끝에서부터 건너뛰므로 프록시가 여러 단이어도 클라이언트 주소를 찾습니다. 신뢰하는 주소에서 연결할 수 있으면 집계될 주소를 스스로 고를 수 있으니, 방화벽으로 프록시만 그 포트에 닿게 하고 프록시가 헤더를 직접 쓰게 하세요(Caddy는 기본 동작, nginx는 `proxy_set_header X-Forwarded-For $remote_addr;`). `0.0.0.0/0`은 거부합니다.
- **프록시가 클라이언트의 `X-Forwarded-For` 줄 뒤에 자기 줄을 따로 붙이는 경우** 클라이언트가 쓴 줄을 읽던 문제를 고쳤습니다. 이제 마지막 줄을 씁니다.
- **듀얼 스택(`--listen [::]:7400`)에서 IPv4 클라이언트**가 `::ffff:a.b.c.d`로 집계되고 이 기기에서 온 연결이 로컬로 인식되지 않던 문제를 고쳤습니다.
- `pumasi ui`가 루프백이 아닌 주소에서 `--real-ip-header`만 있고 `--trusted-proxy`가 없으면 시작할 때 경고합니다.
- [docs/api.md](../api.md)에 제한에 집계되는 것을 적었습니다. 틀리거나 만료·취소된 bearer 티켓과 실패한 로그인만 집계합니다. 티켓이 없는 요청(스캐너의 `401`)과, 유효하지만 권한이 없는 티켓(`403`)은 집계하지 않습니다.
- 프로토콜(14)과 저장 상태 형식(7)은 그대로입니다. 바뀐 것은 `pumasi ui`뿐이라 대시보드나 API를 제공하는 기기만 올리면 됩니다.
