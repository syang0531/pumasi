# Pumasi 1.7.0

Run the cluster from the browser. Sign-ins survive a `pumasi ui`
restart or upgrade, everything the dashboard showed read-only can be
changed there, a node's working hours and slots are set from the node's
page, upgrades can go to a few canary nodes first, charts stream, and
the pages work on a phone.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14) and the stored state's layout (7) are unchanged; a 1.6
cluster upgrades with `pumasi upgrade latest` (or the dashboard's Upgrade
button). Upgrade the control plane first: sessions, node settings and
canaries need it on 1.7, and node settings need the agent on 1.7 too. A
1.7 dashboard in front of an older control plane keeps its sign-ins in
memory as before.

## New

- **Sign-ins that survive restarts.** The control plane keeps the
  dashboard's sessions in its state (only a hash of each session's
  secret), so restarting `pumasi ui`, upgrading it, or failing over to
  another control plane no longer signs anyone out. **Settings** lists
  the browsers signed in (with their browser and address) and revokes
  them; `pumasi access sessions [--revoke ID]` and
  `GET`/`DELETE /api/v1/sessions` do the same. A session ends after 12
  hours unused, on sign-out, or when its ticket is revoked or rotated.
- **Edit in the browser.**
  - Events: the alert rules (node offline, failure rate, disk,
    temperature, benchmark drop, SMART, check mismatches), repeat and
    resolved notices, and webhooks (add, test, remove).
  - Prices: rates, storage prices and default quota, prepaid or mutual
    ledger, hold, check rate and strikes.
  - Schedules (new page): add or replace a cron schedule from a job.toml
    and its files, run one now, remove one.
  - Settings: a `cluster.toml` editor filled with the nodes' labels,
    taints and cordons and the alert rules. **Preview** shows what
    `apply` would change; **Apply** applies it. Also
    `POST /api/v1/apply`.
- **A node's availability from its page.** Slots, CPU share, hours, idle
  minutes and AC power only: the agent writes them to its `agent.toml`
  and restarts with them as soon as its running tasks end (it takes no
  new ones meanwhile). From the CLI: `pumasi node set NODE --slots 2
  --hours 22:00-07:00` (`--default-slots`, `--all-cpus`, `--any-power`,
  `--no-idle`, `--any-time` undo). Needs the agent installed as a
  service (`pumasi service install`); one started by hand says so.
- **Canary rollouts.** `pumasi upgrade latest --canary imac` (or
  `rollout FILES --canary os=windows`) upgrades those nodes first; the
  rest follow once the canaries run the new binary, have finished
  `--canary-tasks` tasks cleanly and `--canary-soak` (default 30m) has
  passed. A canary that fails to install or reports a node error halts
  the rollout; `pumasi upgrade promote [NODE...]` upgrades more nodes or
  all of them, `pumasi upgrade cancel` stops. `--canary-hold` waits for
  promote even when all is well. The dashboard's Upgrade panel picks the
  canaries with checkboxes and shows the canary's state with "Upgrade
  checked next", "Promote all" and "Cancel rollout".
- **Streaming charts.** A node's charts update over server-sent events as
  new samples arrive, instead of a 10-second page refresh.
- **Phones.** Forms stack in one column, inputs do not zoom, the menu
  scrolls sideways, and no page scrolls sideways at phone width.

## Notes

- The `cluster.toml` editor refuses schedules (they name job files) and
  webhook `url_env` (both would be read on the dashboard's machine), and
  never prunes; `pumasi apply` keeps doing all of that.
- The Upgrade panel's canary checkboxes appear when a published release
  is newer than some node; canaries for binaries you built are
  `pumasi upgrade rollout --canary`.
- A program's own failure (a non-zero exit) does not halt a canary; a
  node error (the run could not be done) does.
- Checked by hand, not in CI: changing an alert rule and a node's hours
  from a phone through a tunnel, and a canary upgrade of the home
  cluster. CI covers every new form, a `pumasi ui` restart that keeps the
  sign-in, a canary rollout between two local agents (passing and
  halting), and node settings written to an agent's options file.

## 한국어 요약

- **재시작해도 로그인 유지.** 대시보드 세션을 컨트롤 플레인 상태에 저장합니다(세션 비밀값은 해시만). `pumasi ui`를 다시 시작하거나 업그레이드해도, 다른 컨트롤 플레인으로 넘어가도 로그아웃되지 않습니다. **설정** 페이지에서 로그인한 브라우저 목록을 보고 취소할 수 있습니다(`pumasi access sessions [--revoke ID]`, API도 지원). 12시간 쓰지 않거나, 로그아웃하거나, 티켓이 취소되면 끝납니다.
- **브라우저에서 편집.** 이벤트 페이지에서 경보 규칙·반복/해제 알림·웹훅을, 요금 페이지에서 단가·저장 요금·원장 방식·보류 기간을, 새 **예약 작업** 페이지에서 cron 예약 추가·지금 실행·삭제를 합니다. **설정**의 `cluster.toml` 편집기는 노드 라벨·테인트·격리와 경보 규칙을 채워 보여 주고, **미리 보기**로 바뀔 내용을 확인한 뒤 **적용**합니다.
- **노드 작업 조건을 노드 페이지에서.** 슬롯, CPU 비율, 시간대, 유휴 시간, 전원 연결 시에만을 바꾸면 에이전트가 `agent.toml`에 쓰고, 실행 중인 태스크가 끝나는 대로 새 설정으로 재시작합니다. CLI는 `pumasi node set 노드 --slots 2 --hours 22:00-07:00`. 서비스로 설치한 에이전트만 됩니다.
- **카나리 롤아웃.** `pumasi upgrade latest --canary imac`은 그 노드를 먼저 올리고, 새 바이너리로 `--canary-tasks`개 작업을 문제없이 마치고 `--canary-soak`(기본 30분)이 지나면 나머지가 따라갑니다. 카나리가 설치에 실패하거나 노드 오류를 내면 멈추고, `pumasi upgrade promote [노드...]`나 `pumasi upgrade cancel`로 진행합니다. 대시보드 업그레이드 패널에서 체크박스로 카나리를 고르고 상태를 봅니다.
- **실시간 차트와 휴대폰 화면.** 노드 차트가 서버 전송 이벤트로 바로 갱신되고, 폰 폭에서 폼이 한 줄로 쌓이며 옆으로 스크롤되지 않습니다.
- **업그레이드.** 프로토콜(14)과 저장 형식(7)은 그대로입니다. 컨트롤 플레인을 먼저 올리세요. 세션·노드 설정·카나리는 컨트롤 플레인이 1.7이어야 하고, 노드 설정은 에이전트도 1.7이어야 합니다.
