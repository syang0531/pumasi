# Pumasi 1.8.0

The file store on several machines. Dataset versions are kept on
several copies (control plane replicas and your own nodes labelled for
storage), a write is acknowledged once the copies have it, damaged or
lost copies are found and made again, and `pumasi ui` speaks enough S3
for `aws s3`, rclone and boto3.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14, minor 4) and the stored state's layout (7) are
unchanged; a 1.7 cluster upgrades with `pumasi upgrade latest` (or the
dashboard's Upgrade button). Upgrade every control plane first: storage
nodes need the control plane and their agent on 1.8, and a 1.7 control
plane replica neither confirms writes nor keeps release binaries. 1.7
agents keep working; they are just not storage nodes.

## New

- **Copies on your own machines.** Label owner nodes with spare disk
  `storage=SIZE` (`pumasi node label nas storage=500G`; `storage=yes`
  keeps up to 90% of the disk). Every dataset version is kept on 2
  copies by default, each control plane replica counting as one:
  `pumasi store copies --default 3`, or per dataset `pumasi store copies
  corpus 1` (`default` goes back to the cluster's number). Copies go to
  the storage nodes with the most room, never past a node's quota, and
  `pumasi store replicas [NAME]` shows where each version is and each
  storage node's quota, use and last scrub. Jobs mount datasets from
  replica holders too.
- **Writes on enough copies.** `pumasi store put`, the dashboard's
  upload, S3 writes and job output datasets answer once the version is
  on every control plane replica and on as many storage nodes as it can
  be (up to 5 minutes), so a failover right after a write no longer loses
  it. `store put` says how many copies it got.
- **Repairs.** A storage node removed, or offline longer than
  `cluster start --replica-repair-after` (6h), has its copies made again
  elsewhere. A control plane missing versions (a lost or emptied `blobs`
  directory, a restore without it) fetches them back from the storage
  nodes within a minute (`store.repaired` events, or a critical
  `store.missing` when no copy is left).
- **Scrubs.** Every store is read back and checked against its BLAKE3
  hashes each `--scrub-every` (7d), or now with `pumasi store scrub
  [NODE]` or the Storage page's button. A damaged copy on a node is
  dropped and fetched again; damage on the control plane raises a
  critical `store.damaged` event (repair: restart it with its `blobs`
  directory moved aside).
- **Release binaries on every control plane.** Binaries uploaded for a
  rollout are copied to the control plane replicas, so `pumasi upgrade`
  keeps working after a failover.
- **S3 gateway.** `pumasi ui` serves an S3-compatible API at `/s3` (also
  with `--api-only`): buckets are datasets, objects the files of their
  latest version. `pumasi s3 create-key` (or the Storage page) makes a key
  that acts as your ticket, so a submitter's key writes only its
  account's datasets and a viewer's only reads; `pumasi s3 keys` and
  `pumasi s3 revoke-key` manage them. GetObject (ranges), HeadObject,
  PutObject, CopyObject, DeleteObject(s), ListObjects v1 and v2,
  ListBuckets, CreateBucket, DeleteBucket and multipart uploads work,
  with SigV4 headers, presigned URLs, streamed uploads and CRC32/SHA-256
  checksums. Point clients at `http://127.0.0.1:7400/s3` with path-style
  addressing and any region.
- **Storage page.** Each version's copies (and which nodes hold them),
  the storage nodes with their quotas, use, free disk and last scrub,
  the number of copies (cluster default and per dataset), a scrub button,
  and your S3 keys.

## Notes

- Only owner nodes keep copies; providers' machines never do.
- Each S3 write makes a new dataset version that replaces the version
  the gateway's previous write made (S3 buckets have no versions);
  versions made with `store put` or by jobs are kept. Writes to a bucket
  that arrive together are committed together.
- The gateway has no ACLs, bucket policies, tags, object versions or
  locks, and refuses a key that would be both a file and a folder (`a`
  and `a/b`), since a dataset is a file tree. Files written other ways
  have an ETag made from their BLAKE3 hash (`<hex>-1`), not an MD5.
- Signature Version 2 (boto3's default for presigned URLs on custom
  endpoints) is refused: use `signature_version="s3v4"`.
- Checked in CI: the control plane's `blobs` directory deleted and every
  dataset fetched back from storage nodes, copies made again after a node
  is removed, a damaged replica found by a scrub, and
  `scripts/s3-gateway.sh` running the AWS CLI (cp, sync, multipart,
  s3api), rclone (sync, check) and boto3 against the gateway. By hand:
  a dataset survives moving the control plane to another PC without
  copying `blobs`.
