# Pumasi 1.9.0

Scheduling that knows more about your jobs. A job's tasks can start
together or not at all, spread over machines or zones, run next to or away
from another job; accounts can be capped in CPUs and memory, also on the
machines a label picks; a task that has to move saves a checkpoint and
goes on from it on the next machine; and schedules run in any time zone.

## Install

```sh
curl -fsSL https://github.com/syang0531/pumasi/releases/latest/download/install.sh | sh
```

On Windows, from an administrator PowerShell:
`irm https://github.com/syang0531/pumasi/releases/latest/download/install.ps1 | iex`.
The protocol (14, minor 5) and the stored state's layout (7) are
unchanged; a 1.8 cluster upgrades with `pumasi upgrade latest` (or the
dashboard's Upgrade button). Upgrade the control plane first. Checkpointing
tasks go only to 1.9 agents; 1.8 agents keep running everything else.

## New

- **Gangs.** `gang = true` in job.toml starts all of a job's tasks
  together or none of them; when one has to move or is retried, the
  others stop too and the gang starts again together. A gang of higher
  priority stops lower-priority tasks for all its tasks at once.
- **Spreading.** `spread = "node"` (or a label key such as `"zone"`)
  puts each task in the group with the fewest of the job's tasks;
  `spread = { by = "zone", max = 2 }` also caps a group, and the rest
  wait.
- **Affinity and anti-affinity.** `affinity = { near = ["db"], away =
  ["batch"], by = "node" }` keeps tasks where tasks of the named jobs (of
  the same account, by name or id) run now, and away from where the
  others run; `by` can be a label key (`"rack"`, `"zone"`).
- **CPU and memory quotas.** `pumasi quota alice --cpus 16 --memory 64G`
  caps the whole CPUs and memory an account's running tasks hold (a WASM
  task holds one CPU), and `--label-quota "zone=office slots=4 cpus=8
  memory=16G gpus=1"` (repeatable) caps what it holds on the nodes a
  selector picks. Also on the dashboard's Accounts page, in cluster.toml
  (`cpus`, `memory`, `[[accounts.NAME.label_quotas]]`) and over HTTP
  (`GET /api/v1/resources`, `PUT /api/v1/accounts/NAME/resources`).
- **Checkpoints.** With `checkpoint = true` (or `{ grace = "1m" }`), a
  task that has to move (preemption, `pumasi drain`, a machine paused with
  `--on-pause requeue`, a machine going to sleep, a gang mate moving) gets
  SIGTERM and its grace period (30 s by default, 10 minutes at most)
  instead of being killed. What it wrote to `/checkpoint`
  (`$PUMASI_CHECKPOINT`) goes to the file store, and the next run starts
  with it there, on any machine; the move does not count as an attempt.
  `pumasi job ID` and the job's page list each task's checkpoint and how
  often it resumed. [`examples/checkpoint`](../../examples/checkpoint)
  estimates pi over a long run that can be drained halfway.
- **Schedules in a time zone.** `pumasi schedule add NAME job.toml --cron
  "0 9 * * *" --tz Asia/Seoul`, `tz = "Asia/Seoul"` in cluster.toml, or
  the Schedules page. The schedule list shows the zone after the cron
  line.
- **Why it waits.** A job held back by its placement says why, per node
  (`a (1 of the job's tasks already run in its zone)`), in `pumasi job`,
  on its page and in `GET /api/v1/jobs/ID/placement`.

## Notes

- Docker and WASM tasks can checkpoint; microVM tasks cannot yet (such a
  job is refused). A WASM task cannot catch a signal, so it is stopped at
  once with what it has saved so far: write the checkpoint as you go
  (to a temporary file, then rename it).
- A checkpoint is saved when a task is moved, not periodically: a
  machine that dies without warning loses the progress since the last
  move. A sleeping machine gives its tasks 10 seconds in all.
- A task asked to stop keeps its slot until it has saved its checkpoint,
  so the task that preempted it starts a few seconds later than before.
- Checkpoint data is removed from the store when the job ends; its record
  (size, node, resumes) stays until the job expires.
- Deterministic WASM jobs cannot checkpoint (a checkpointing WASM job is
  not deterministic by default), nor can confidential jobs.
- Checked in CI: a checkpointing task moved off a drained node finishes
  on another without starting over (WASM always, Docker where the runner
  has it), gangs that wait for room for all their tasks, spreading,
  affinity, CPU quotas and a schedule in Asia/Seoul kept across a
  restart.
